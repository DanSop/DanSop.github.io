What Happens Before main()?

February 18, 2022

The first eight bytes of a Cortex-M firmware image are not code. Here they are from a minimal program I built with arm-none-eabi-gcc 10.3 at -O2 for an STM32F0 with 64 KB of flash and 8 KB of RAM:

08000000: 00200020 15000008

The bytes look scrambled because the Cortex-M is little-endian, meaning the least significant byte of a number is stored first. Reading each group of four bytes backwards gives the actual values, 0x20002000 and 0x08000015. On an STM32F0 flash starts at 0x08000000 and RAM at 0x20000000, so the first value is the very top of the 8 KB of RAM (0x20000000 + 0x2000), and the second points into flash. Between them, those two words are most of the answer to what happens before main().

Reset and the Vector Table

When a Cortex-M comes out of reset, the hardware reads the first word of flash into the stack pointer, reads the second word into the program counter, and only then runs its first instruction, at whatever address the program counter now holds. Those first words are the start of the vector table, a list of addresses that also holds the handlers for every interrupt and fault. The STM32 maps the start of flash to address 0x0 when it boots from flash, so the table physically lives at 0x08000000.

The second value is the reset handler’s address, except that Reset_Handler is really at 0x08000014. That extra 1 in the lowest bit tells the CPU to run the code as Thumb instructions, the compact instruction set that a Cortex-M uses. Every handler address in the table has this bit set, and if it were 0 the CPU would fault on its very first instruction.

The stack pointer being loaded first matters more than it looks. Every C function uses the stack for its locals and return addresses, therefore on a lot of other processors the first few instructions after reset have to be written in assembly just to point the stack somewhere sane (on Linux the kernel hands every new process a stack before its first instruction runs). On a Cortex-M the hardware has already done it, so the reset handler can be an ordinary C function. In C the table is just an array of pointers:

__attribute__((section(".isr_vector"), used))
const void *vector_table[] = {
    &_estack,
    Reset_Handler,
    NMI_Handler,
    HardFault_Handler,
};

The section(".isr_vector") attribute tells the compiler to put the array in its own section so the linker can place it first in flash, and used stops the compiler from removing it, since no C code ever reads it. _estack is the address of the top of RAM, which comes from the linker script further down.

Where Variables Live

Here is the program I will be starting:

uint32_t boot_count = 42;
uint32_t ticks;

int main(void)
{
    boot_count++;
    ...
}

When the compiler builds this, it sorts everything into the following sections:

  • .text holds the machine code for functions.
  • .rodata holds constants and string literals that never change.
  • .data holds global and static variables that have a non-zero starting value, like boot_count.
  • .bss holds global and static variables that start at zero or have no initializer, like ticks.

.text and .rodata can stay in flash since they never change. .data and .bss are the problem. boot_count changes while the program runs so it has to be in RAM, but RAM is random at power-on, therefore the 42 has to be stored in flash and copied into RAM before main() runs. The C standard also says ticks starts at zero, so that part of RAM has to be cleared before main() as well. Those two jobs are most of what the startup code is for.

The Linker Script

The compiler turns each .c file into an object file containing these sections, but without final addresses. The linker then combines them into one program and decides where every section goes, and for a microcontroller it needs a linker script describing the chip’s memory:

MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 64K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 8K
}

_estack = ORIGIN(RAM) + LENGTH(RAM);

SECTIONS
{
    .isr_vector : { KEEP(*(.isr_vector)) } > FLASH
    .text       : { *(.text*) *(.rodata*) } > FLASH

    _sidata = LOADADDR(.data);
    .data : { _sdata = .; *(.data*); _edata = .; } > RAM AT > FLASH

    .bss  : { _sbss = .; *(.bss*) *(COMMON); _ebss = .; } > RAM
}

The MEMORY block lists where flash and RAM are and how big they are. In SECTIONS, > FLASH and > RAM say which memory each section goes into, and the vector table is listed first so it ends up at the very start of flash.

On the .data line, > RAM AT > FLASH gives .data two addresses: the address it runs from in RAM, and the address where its initial values are stored in flash. The . in the script means the current address, so _sdata = .; and _edata = .; record where .data starts and ends in RAM, and LOADADDR(.data) gives the address of its copy in flash. _sbss and _ebss do the same for .bss.

These names are linker symbols, not variables. A linker symbol is just an address, therefore in C they are declared as extern and only ever used with &:

extern uint32_t _sidata, _sdata, _edata, _sbss, _ebss, _estack;

Here &_sdata is the address where .data starts. Reading _sdata itself reads whatever happens to be stored at that address, which is the classic first mistake with these.

The symbol table of the built program shows where everything landed:

Symbol Address Meaning
_sidata 0x08000078 where the initial values of .data are stored in flash
_sdata / boot_count 0x20000000 start of .data in RAM
_edata / _sbss 0x20000004 end of .data, start of .bss
ticks 0x20000004 the zero-initialized variable
_ebss 0x20000008 end of .bss
_estack 0x20002000 top of RAM, the initial stack pointer

The value 42 for boot_count is stored in flash at 0x08000078, and the variable itself lives in RAM at 0x20000000.

The Reset Handler

With those symbols the reset handler is a short C function:

void Reset_Handler(void)
{
    uint32_t *src = &_sidata;
    uint32_t *dst = &_sdata;

    while (dst < &_edata)
    {
        *dst++ = *src++;
    }

    dst = &_sbss;
    while (dst < &_ebss)
    {
        *dst++ = 0U;
    }

    main();

    while (1)
    {
    }
}

Firstly, the first loop copies .data one 32-bit word at a time, reading from flash through src and writing to RAM through dst, until dst reaches the end of .data. Secondly, the second loop writes zero to every word from the start to the end of .bss. Copying a word at a time is safe because vendor linker scripts pad each section to a multiple of 4 bytes with ALIGN(4). The infinite loop after main() is there because there is nothing to return to, therefore it is the only sane place to park the CPU.

The compiler turns this into two small loops of instructions:

800002c:  ldr    r4, [r0, r3]     ; load a word from flash into r4
800002e:  str    r4, [r1, r3]     ; store r4 into RAM
8000030:  adds   r3, #4           ; move to the next word
8000032:  cmp    r3, r2           ; reached the end of .data?
8000034:  bne.n  800002c          ; if not, go back
   ...
800004c:  stmia  r3!, {r1}        ; store r1 (zero) and advance r3
800004e:  cmp    r3, r2           ; reached the end of .bss?
8000050:  bne.n  800004c          ; if not, go back
8000052:  bl     800006c <main>   ; call main, return address saved in LR

The numbers on the left are the addresses of each instruction in flash, which is what the program counter steps through. stmia stores a register and moves the pointer forward in one instruction, and bl is the call into main, which saves the return address in the link register and loads the address of main into the program counter.

A real project uses the vendor’s startup file instead of writing its own, and it does the same two loops plus a little more before calling main(): it calls SystemInit() to set up the clocks, since the chip comes out of reset on a slow internal oscillator, switches the FPU on for parts that have one (until then the first floating point instruction faults), and calls __libc_init_array() to run C++ constructors and anything marked __attribute__((constructor)).

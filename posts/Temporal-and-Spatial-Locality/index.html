Temporal and Spatial Locality

November 19, 2026

Every cache is a bet that the future will look like the past. Hume spent a good part of the 1700s pointing out that there is no logical reason it should (the sun rising every morning so far proves nothing about tomorrow), and yet every desktop CPU is built on exactly that bet: whatever you touched a moment ago you will probably touch again, and whatever sits right next to it you will probably want next. Those two assumptions are temporal and spatial locality, and I wanted to know what the bet is actually worth, both when it pays off and when it does not.

So I wrote a few small benchmarks and ran them on my laptop, an AMD Ryzen 9 8945HS with 32 KB of L1 data cache and 1 MB of L2 per core and 16 MB of L3 shared between them. Everything was built with GCC 16.2 at -O2, run under WSL2 pinned to a single core, and every number below is the median of five runs.

Temporal Locality

To see what the cache is worth, the benchmark first has to make it impossible to guess anything. I built a buffer of 64-byte nodes, one per cache line, linked every node into a single random cycle, and then just followed the pointers:

// One node per cache line, so every hop lands on a new line
typedef struct chase_node
{
    struct chase_node *next;
    uint8_t padding[CACHE_LINE_SIZE - sizeof(struct chase_node *)];
} chase_node_t;

chase_node_t *node = &nodes[order[0]];

for (uint32_t i = 0U; i < NUM_CHASE_LOADS; i++)
{
    node = node->next;
}

Every load needs the address that the previous load returns, so nothing can start early, and the random order leaves no pattern to learn. What is left is the raw latency of wherever the buffer happens to fit, and growing the buffer walks it down the memory hierarchy (Figure 1, “Random order”).

While the whole cycle fits in the 32 KB of L1, a load takes 0.8 ns, about four clock cycles. Past that it steps up to 2.8 ns in L2, somewhere between 10 and 15 ns in L3, and once the buffer outgrows the 16 MB of L3 it climbs to 126 ns at 512 MB, which is DRAM plus a page table lookup on nearly every load. The steps do not land exactly on the cache sizes (the buffer is not the only thing living in the cache, and Windows is still running underneath WSL), and right at each boundary the numbers moved by up to a third between runs. Away from the boundaries they repeated within a few percent. Same loop, same number of instructions, and a factor of 160 between the two ends.

Spatial Locality

Spatial locality is the other half of the bet. Memory moves between the levels a whole 64-byte line at a time, so reading one byte drags its 63 neighbours along for free, and the only way to see what that is worth is to stop using the neighbours. Figure 2 reads one byte every stride bytes across a 1 GB buffer, far bigger than L3.

Up to 64 bytes the time per access roughly doubles every time the stride doubles, from 0.4 ns at an 8-byte stride to 2.3 ns at 64. That is just one line being shared between fewer and fewer accesses, until every access gets a line to itself. Past that it creeps up to about 6.7 ns, and at 4 KB it jumps to 10.5 ns and stays there. 4 KB is the page size, therefore from there on every access lands on a new page and needs its own page table lookup, and hardware prefetchers generally will not follow a stream across a page boundary either.

The Prefetcher

The other line in Figure 1, “Front to back”, reads exactly the same working sets in order, and it barely moves. It takes about 0.8 ns per cache line while the data fits in cache and only 1.3 ns per line with 512 MB in DRAM, which is roughly 48 GB/s from a single core. The DRAM did not get any faster. The prefetcher watched the addresses climb one line at a time and started fetching lines before the loop asked for them, so by the time each load happens the data is already sitting in cache.

This is the part of the machine I find the most cybernetic. Norbert Wiener’s anti-aircraft predictor in the 1940s took the past path of a plane and extrapolated where it would be by the time a shell got there. A stride prefetcher is the same idea moved into the memory system, extrapolating where your loop will be by the time a cache line can get there. It only knows the past, and it is only right because most loops are boringly predictable.

Layout decides how predictable a program looks, even when the code does not change at all. I built the same 4 million node linked list twice, each node padded to one cache line, once with the nodes laid out in memory in list order and once scattered at random, and walked both with the same loop:

for (list_node_t *node = head; node != NULL; node = node->next)
{
    sum += node->value;
}

In order it takes 2.4 ns per node. Scattered it takes 119 ns per node, 50 times slower, and the only thing that changed is where the nodes ended up.

When Nothing Can Be Predicted

The last benchmark was supposed to be the one where software prefetching saves the day. It reads random elements out of a 512 MB array, data[index[i]], and optionally asks for the element distance iterations ahead with __builtin_prefetch:

for (size_t i = 0U; i < GATHER_LENGTH; i++)
{
    if ((distance != 0U) && ((i + distance) < GATHER_LENGTH))
    {
        __builtin_prefetch(&data[index[i + distance]]);
    }
    sum += data[index[i]];
}

Without any prefetching it already only takes 9.5 ns per element, which looks wrong at first, since every one of those reads is a random access into DRAM and DRAM was costing 125 ns a moment ago. The best prefetch distance only brought it down to 7.4 ns.

The difference between the scattered list and the random gather is the whole point. In the list the address of the next node lives inside the current node, therefore the CPU cannot even start the next load until the current one comes back, and every node pays the full trip to DRAM. In the gather every address comes from index[], which is read front to back, so the out-of-order core can keep a pile of loads in flight at once. At 9.5 ns per element against roughly 125 ns of latency, that is about 13 loads overlapping. The prefetch hint only had the leftover 22% to work with, since the core was already doing most of the job on its own.

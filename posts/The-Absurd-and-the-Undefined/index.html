The Absurd and the Undefined

October 21, 2022

GCC 12 compiles this function to return 1;:

int will_overflow(int x)
{
    return x + 1 > x;
}

mov    eax, 0x1          // return value = 1
ret

Mathematically x + 1 > x is always true, but in 32-bit arithmetic it should not be when x is INT_MAX, since x + 1 wraps around to INT_MIN. GCC does this even at -O0.

The reason is that the C standard lists a long set of things a valid program never does: overflow a signed integer, access an object through a pointer of the wrong type, dereference a null pointer, and so on. If a program does one of them anyway, the standard places no requirements at all on what happens, and compilers read that as permission. A valid program never overflows a signed integer, therefore the compiler is allowed to assume a signed addition never overflows and to optimize on that basis. Every listing here comes from GCC 12 for x86-64 at -O2 (plus -fcf-protection=none), so any of them can be pasted into Compiler Explorer.

Making x unsigned, where wrapping is defined, keeps a real comparison, and so does compiling the signed version with -fwrapv, which tells GCC that signed overflow wraps:

xor    eax, eax          // result = 0
cmp    edi, 0x7fffffff   // is x == INT_MAX?
setne  al                // result = (x != INT_MAX)
ret

With wrapping defined, GCC works out that x + 1 > x is false for exactly one input, INT_MAX, and turns the whole function into x != INT_MAX. Without the flag, an overflow check written as if (x + 1 < x) on a signed type is removed from the program without any warning.

Strict Aliasing

int alias(int *a, float *b)
{
    *a = 1;
    *b = 2.0f;
    return *a;
}

If a and b point at the same memory, the store to *b overwrites *a, so the function should return the bits of 2.0f. The aliasing rules say an int cannot be accessed through a float*, therefore the compiler assumes the two pointers never overlap:

mov    DWORD PTR [rdi], 0x1          // *a = 1
mov    eax, 0x1                      // return value = 1, without re-reading *a
mov    DWORD PTR [rsi], 0x40000000   // *b = 2.0f
ret

It returns 1 straight from a register. With -fno-strict-aliasing, *a is read again after the store to *b:

mov    DWORD PTR [rdi], 0x1
mov    DWORD PTR [rsi], 0x40000000
mov    eax, DWORD PTR [rdi]          // re-read *a
ret

Embedded code runs into this fairly often, for example when reading a byte buffer through a uint32_t* or reinterpreting a float as an integer. The safe way to reinterpret bits is memcpy, which the compiler turns into a register move anyway.

The Deleted Null Check

int read_reg(int *p)
{
    int v = *p;
    if (p == 0)
    {
        return -1;
    }
    return v;
}

Dereferencing a null pointer is undefined, and *p is read first, therefore the compiler concludes that p cannot be null by the time of the check, and removes the check as dead code:

mov    eax, DWORD PTR [rdi]   // return *p
ret

The same pattern caused a Linux kernel vulnerability in 2009, where a null check in the tun driver was removed for exactly this reason. GCC’s -fno-delete-null-pointer-checks keeps the check:

test   rdi, rdi                // is p null?
mov    eax, 0xffffffff         // result = -1
cmovne eax, DWORD PTR [rdi]    // if not null, result = *p
ret

On a desktop the deleted check rarely changes the outcome, since reading address 0x0 crashes the program before the check would run anyway. A Cortex-M is different. Address 0x0 is valid memory there since the vector table is mapped to it, so reading *p with p == 0 does not fault and just hands back the initial stack pointer. The check is the only thing that would have caught the bug, therefore I recommend -fno-delete-null-pointer-checks for every firmware build.

The Linux kernel builds with that flag and -fno-strict-aliasing, plus -fno-strict-overflow, which implies -fwrapv on modern GCC.

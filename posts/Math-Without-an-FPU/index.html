Math Without an FPU

June 10, 2022

The Cortex-M0 has no floating point unit, therefore every float operation in C turns into a call into a software library. Fixed-point does the same math with plain integer instructions and keeps track of the binary point purely by convention, and I wanted to know how big the difference really is on an STM32F072.

Take a function that multiplies two floats, compiled with arm-none-eabi-gcc 10.3 at -O2 for -mcpu=cortex-m0:

float f_mul(float a, float b)
{
    return a * b;
}

It compiles to:

push  {r4, lr}
bl    __aeabi_fmul
pop   {r4, pc}

One bl. Every float multiply is a call into libgcc, which unpacks both numbers into sign, exponent and mantissa, multiplies the mantissas with integer instructions, then normalizes, rounds and packs the result back up. __aeabi_fmul is 588 bytes and __aeabi_fadd is 828 bytes, so the pair costs 1.4 KB of flash, about 9% of a 16 KB part, before a single line of your own code. (__aeabi_lmul, the 64-bit integer multiply, is another 90 bytes, and it comes back later.)

Fixed-Point and Q Formats

Fixed-point stores a fractional number as an integer, with an agreed position for the binary point. A number in \(Q_{m.n}\) format has \(m\) integer bits and \(n\) fraction bits, and its value is:

\[\text{value} = \frac{\text{stored integer}}{2^n}\]

Q15 is a 16-bit signed integer with 15 fraction bits. It covers \([-1, 1)\) in steps of \(2^{-15} \approx 0.00003\), which suits audio samples and filter coefficients. Q16.16 is a 32-bit signed integer split down the middle, covering roughly \(\pm 32768\) in steps of \(2^{-16} \approx 0.000015\).

Two numbers in the same format can be added and subtracted as plain integers:

q16_t q16_add(q16_t a, q16_t b)
{
    return a + b;
}

This compiles to a single adds r0, r0, r1, compared to a call into the 828-byte __aeabi_fadd.

Multiplication

Multiplication needs a shift afterwards. Multiplying two Q15 numbers:

\[\begin{aligned} \frac{a}{2^{15}} \cdot \frac{b}{2^{15}} &= \frac{a \cdot b}{2^{30}} \end{aligned}\]

So the raw product is in Q30 and has to be shifted right by 15 to get back to Q15:

\[\boxed{c = \frac{a \cdot b}{2^{15}}}\]

The product of two 16-bit numbers always fits in 32 bits, so the multiply itself is a single muls instruction.

Rounding

A plain right shift truncates, and since an arithmetic shift rounds toward negative infinity the error is always in the same direction. Over thousands of operations, for example in a filter, that bias accumulates. Adding half of the last bit before shifting turns it into round-to-nearest:

\[c = \frac{a \cdot b + 2^{14}}{2^{15}}\]

Overflow

Q15 can represent \(-1\) but not \(+1\), therefore there is exactly one product that overflows: \(-1 \times -1\). To handle it the result is saturated:

q15_t q15_mul(q15_t a, q15_t b)
{
    int32_t product = (int32_t)a * (int32_t)b;

    // Round to nearest, then drop the extra 15 fraction bits
    product += (1 << 14);
    product >>= 15;

    if (product > INT16_MAX)
    {
        product = INT16_MAX;
    }
    if (product < INT16_MIN)
    {
        product = INT16_MIN;
    }

    return (q15_t)product;
}

GCC compiles this to:

movs   r3, #128
lsls   r3, r3, #7       ; r3 = 0x4000 (2^14)
mov    ip, r3
movs   r3, #128
muls   r1, r0           ; a * b
add    r1, ip           ; + 2^14
asrs   r0, r1, #15      ; >> 15
lsls   r3, r3, #8       ; r3 = 0x8000
cmp    r0, r3           ; did -1 * -1 overflow?
bne.n  16
ldr    r0, [pc, #4]     ; saturate to 0x7fff
sxth   r0, r0
bx     lr

GCC worked out that the result can never go below INT16_MIN, so it removed the second check entirely, and it turned the first check into an equality test against the one value that can overflow. Fairly clever for a compiler.

Q16.16 Needs 64 Bits

For Q16.16 the product of two 32-bit numbers needs 64 bits before the shift. The Cortex-M0 has no 32x32 to 64-bit multiply instruction, so this also becomes a library call, to __aeabi_lmul. That routine is 90 bytes of integer code rather than all the unpacking, normalizing and rounding done by __aeabi_fmul, but on an M0 only Q15 multiplication maps directly onto a hardware instruction.

Benchmark

I ran each routine on a NUCLEO-F072RB (STM32F072, Cortex-M0) clocked from its 8 MHz internal oscillator with zero flash wait states. Each operation runs 1000 times over 64 pairs of random operands. The Cortex-M0 has no cycle counter, so the timing comes from the SysTick timer, which counts core clock cycles:

#define NUM_ITERATIONS  1000U
#define NUM_OPERANDS    64U
#define SYSTICK_MAX     0x00FFFFFFU

static uint32_t run_float(float (*operation)(float, float))
{
    SYST_RVR = SYSTICK_MAX;
    SYST_CVR = 0U;
    SYST_CSR = 0x5U;  // enable SysTick, clocked from the core clock

    for (uint32_t i = 0U; i < NUM_ITERATIONS; i++)
    {
        uint32_t n = i % NUM_OPERANDS;

        g_floatResult = operation(g_floatA[n], g_floatB[n]);
    }

    return SYSTICK_MAX - SYST_CVR;
}

The same loop calling an empty function took 23 cycles per iteration, and that baseline is subtracted from each result:

Operation Cycles per op vs. float multiply
float multiply 166 1x
float add 120 1.4x faster
Q16.16 multiply 81 2x faster
Q15 multiply 13 13x faster
Q16.16 add 1 166x faster

166 cycles against 13 for the same multiply, and a float add costs as much as 120 fixed-point ones. Q16.16 multiply only gets to twice as fast, because its 64-bit product still goes through __aeabi_lmul. And once __aeabi_fmul and __aeabi_fadd are linked in, they take up their 1.4 KB whether they are called once or a million times.
